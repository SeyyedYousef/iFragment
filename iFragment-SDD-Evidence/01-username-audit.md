- # Telegram / Fragment Username Vertical Audit

**Repository:** `/home/user/work/ifragment_audit/src/iFragment-main`  
**Scope:** username-only vertical: backend, frontend, API/router/schema, migrations, valuation/collection workers, Fragment/TON integrations, tests, and relevant documentation.  
**Audit mode:** read-only static review; no source-code changes were made.  
**Finding priorities:** P0 = immediate security, money, or materially false-data risk; P1 = release-blocking correctness/contract/data-integrity risk; P2 = important quality, observability, or maintainability risk.

---

## Executive summary

The username vertical has a coherent high-level flow—search/check, paywall/access, valuation, provenance enrichment, and a single-item report—but the implementation currently mixes live observations, scraped data, database data, static anchors, deterministic fallbacks, and synthetic UI data. The most serious risks are:

1. **P0 money/access risks:** potentially double deduction of FRG credits, non-atomic Pro quota consumption, and order-status endpoints without ownership checks.
2. **P0/P1 false-data risks:** static historical sales and collection defaults are surfaced as live/on-chain/verified data; the collection chart is generated with trigonometric synthetic points.
3. **P1 contract gaps:** OpenAPI paths do not match runtime routes; several documented username endpoints are not registered; frontend status and payment contracts drift from backend behavior.
4. **P1 privacy/security risk:** 24-hour report cache is keyed only by username and is not bound to Telegram account identity.
5. **P1 provenance risk:** “cryptographic certificate” is only an unsigned SHA-256 digest and can be generated by anyone.

The report should not be interpreted as a claim that every static number is factually wrong; the issue is that the code does not preserve or expose sufficient provenance to distinguish verified observations from estimates, anchors, copied snapshots, or emergency defaults.

# Findings

## F-01 — Double FRG deduction and non-atomic balance handling

- **Priority / severity:** **P0 / Critical**
- **Files:** `backend/internal/handler/username_public.go:1557-1581`; `backend/internal/repository/profile_repo.go:5862-5937`
- **Current behavior:** `ValuationPayAirdrop` opens a transaction, calls `DeductCreditsFIFO`, then separately executes `UPDATE user_stats SET airdrop_coins = airdrop_coins - $1`. `DeductCreditsFIFO` itself already recomputes/synchronizes `user_stats.airdrop_coins` from credit batches. The second update can deduct twice. The handler also does not check `RowsAffected()` on the second update, so a zero-row update can still be followed by a paid order and access grant. The pre-transaction balance check is also not the authoritative lock-protected check.
- **Expected behavior:** One successful report unlock consumes exactly one configured amount exactly once. Insufficient balance, stale balance, concurrent requests, and failed order insertion must leave both credits and entitlement unchanged.
- **Acceptance criteria:**
  - One database transaction owns balance validation, FIFO consumption, order creation, and entitlement creation.
  - There is one authoritative balance mutation only.
  - Every balance `UPDATE` checks affected rows or relies on a locked batch ledger with invariant checks.
  - Repeated/concurrent requests cannot create two paid entitlements for one deduction.
  - An order is never marked paid if deduction or entitlement persistence fails.
- **Test cases:**
  1. Balance exactly equals price: one deduction, paid order, access granted.
  2. Balance one unit below price: no deduction/order/access.
  3. Two concurrent requests with one sufficient balance: exactly one succeeds.
  4. Failure during order insert: transaction rolls back all credit mutations.
  5. Retry with same logical report: idempotent result, no second deduction.

## F-02 — Collection seed/default data can be presented as live data

- **Priority / severity:** **P0 / Critical data-integrity**
- **Files:** `backend/internal/service/username/collection_worker.go:182-241`; `:443-461`; `:485-565`; `:588-669`
- **Current behavior:** Empty databases are seeded with constants including `582.8K`, `164.6K`, `5.49 TON`, `124.0M TON`, category volumes, and hardcoded auction/sales/activity handles. Failed upstream calls copy the latest snapshot or insert more defaults. The response has no `source`, `fetched_at`, `stale`, `is_estimate`, or confidence indicator. The frontend can therefore render emergency/default data as current collection intelligence.
- **Expected behavior:** Every aggregate/list item is provenance-bearing. A fallback must be explicitly labeled stale/estimated and must not receive a “live”, “verified”, or “on-chain” presentation.
- **Acceptance criteria:**
  - Schema stores source, fetch timestamp, parser version, stale/fallback state, and provenance URL or record ID.
  - API exposes provenance and current-vs-stale state.
  - UI distinguishes live, last-known, estimated, and unavailable states.
  - Synthetic emergency rows are either removed from production responses or explicitly marked `synthetic=true`.
- **Test cases:**
  1. GetGems timeout with empty DB returns `pending/unavailable`, not a live-looking default.
  2. Upstream timeout with existing snapshot returns `stale=true` and original fetch timestamp.
  3. Default seed rows cannot satisfy a `verified/on-chain` UI condition.
  4. UI snapshot test confirms fallback label is visible.

## F-03 — Collection price/volume chart is fully synthetic

- **Priority / severity:** **P0 / Critical false-analytics**

- **Acceptance criteria:**
  - API provides real points or the chart is removed/replaced by a clearly labeled single snapshot.

  - “Verified” is conditional on actual source evidence.
- **Test cases:**
  1. Network fixture with two points renders exactly those two points.
  2. Empty time series renders “history unavailable”, not generated points.
  3. Snapshot test rejects “Verified” label when provenance is absent.
  4. Property test ensures changing current floor alone does not fabricate historical movement.

## F-07 — “Cryptographic certificate” is an unsigned public SHA-256 digest

- **Priority / severity:** **P0 / Critical trust/security**
- **Files:** `backend/internal/service/username/avm/valuation.go:203-207`; `:1815-1818`; `:1860-1863`
- **Current behavior:** Certificate signature is `sha256(username:model:expected:confidence:timestamp)`. Verification recomputes that public hash. There is no secret/private key, key ID, signature expiry, or server authenticity. Anyone can generate a valid-looking certificate for arbitrary values.
- **Expected behavior:** A certificate must authenticate issuer and bind report content/version/time through HMAC or asymmetric signing. Public verification must know the trusted key and accepted timestamp/model policy.
- **Acceptance criteria:**
  - Use a server-held HMAC secret or asymmetric private key.
  - Include key ID, canonical payload, issued/expiry timestamps, model version, and report/run ID.
  - Verification rejects forged signatures, expired certificates, and unsupported versions.
  - UI wording is “hash/checksum” until authenticity is implemented.
- **Test cases:**
  1. Attacker-generated plain SHA-256 is rejected.
  2. Tampering with expected price/confidence/time fails verification.
  3. Valid signature from active key succeeds.
  4. Retired key policy behaves as documented.

## F-08 — Browser report cache is not bound to Telegram account

- **Priority / severity:** **P0 / High privacy**

- **Test cases:**

  2. Account switch removes report payload/index.
  3. Anonymous browser cannot access prior authenticated cache.
  4. Expired cache is pruned from both payload and index.

  2. Bumping the canonical version invalidates public valuation cache and certificate verification policy.
  3. Calibration refuses to label a different model version as the active model.

# Collection vs. single-item report gaps

## P0 gaps

1. **Truthfulness boundary is missing in both surfaces.** Collection defaults/chart and single-item static anchors are both rendered with live/on-chain/verified language. Fix provenance and UI state before using either surface for financial decisions. Sources: F-02, F-03, F-05, F-06, F-17.
2. **Payment/access security is not isolated to a single-item report.** The single-item path is monetized, but its order status and cache controls are weaker than the sensitivity of the report. Fix F-01, F-08, F-12, and F-13 before production monetization.
3. **Certificate trust is shared by the single-item report.** The report’s “cryptographic” certificate is forgeable. Fix F-07 before exposing it as proof or allowing it to influence marketplace decisions.

## P1 gaps

1. **Collection is snapshot-oriented but UI claims time-series intelligence.** Backend stores daily string snapshots and small child lists; frontend renders a multi-timeframe chart and “liquidity verified” status. There is no real historical points API. Sources: `backend/internal/repository/collection_repo.go:47-150`, `frontend/src/pages/collection-info/ui/UsernameCollectionChart.tsx:27-89`.
2. **Collection and single-item use different source/provenance models.** Collection tables store strings (`items_count`, `floor_price`, `total_volume`) and no source/fetch metadata, while AVM has richer `reasoning_log`, `DataBadges`, and `valuation_runs` but still conflates static anchors with sales. A common observation/provenance schema is needed.
3. **Collection status does not feed AVM coherently.** Collection aggregate `floor_price`/volume are read by collection UI, while the single-item AVM builds a separate `MarketContextDto` and uses live/scraped/DB data. There is no declared freshness or reconciliation contract between them.
4. **Collection listing data is not suitable for arbitrage.** Collection worker writes `nft_collection_recent_auctions`; arbitrage worker reads `nft_collection_auctions`, and comma-separated TON prices are not parsed correctly. Source: F-15.
5. **Single-item report has more detailed source claims but fewer route-level tests.** Direct handler tests cover methods that are not actually routed; collection has no comparable integration coverage. Add router/API contract and database fixture tests for both surfaces.
6. **API naming is inconsistent.** Collection UI calls `/collection/stats`, OpenAPI advertises `/usernames/collection/stats`, and the single-item UI calls `/usernames/valuate` while OpenAPI still describes v7.0. Consolidate paths and generated types.

## P2 gaps

1. Collection fallback/empty/error states are not modeled as a reusable state machine; single-item report has multiple fallback/locked/error states but no shared provenance component.
2. Collection Hall of Fame and single-item similar/comparable cards duplicate hardcoded/archive market concepts with different badges (`verified`, `archive_anchor`, `historical sale`). Normalize evidence labels.
3. Model version and calibration labels drift across the two surfaces. Single-item UI says AVM v7.0 in discovery; backend model is v8.1. Collection UI says “Fragment Index” without a model/data version.
4. Collection and single-item tests rely heavily on mocks/static fixtures and do not exercise scraper/schema failure, stale data, quota races, or browser account switching.

# Valuation/collection algorithm map

## AVM mathematical path

1. `ValuationService.Valuate` canonicalizes username and deduplicates concurrent work with SingleFlight (`backend/internal/service/username/avm/valuation.go:765-775`).
2. `valuateInternal` validates length/characters and classifies segment/features (`:778-798`).
3. Parallel fetches DB target/exact/broad comparables, momentum, MarketApp item/scrape, Fragment status, and Fragment historical sales (`:800-901`).
4. Scraped sales are merged and may be persisted to `username_sales` as `fragment_scrape` (`:929-970`).
5. Static historical/anchor records can be injected (`:972-1002`).
6. Cohort appreciation is applied; semantic scoring can influence the prior (`:1004-1040`).
7. `CalcBaseLog` performs normalization to length-5, Winsorization, time decay, weighted median/MAD, hierarchical Bayesian shrinkage, and denormalization (`backend/internal/service/username/avm/math_engine.go:197-340`).
8. Morphology, momentum, market regime, uncertainty, and confidence are applied in the remaining AVM path.
9. Audit write inserts into `valuation_runs`; on failure, a synthetic timestamp-derived run ID is returned (`valuation.go:1558-1587`).
10. The result is enriched with history, portfolio, owner profile, risk, market context, certificate, badges, and fallback flags (`valuation.go:1589-1900`).

## Collection path

1. `CollectionWorker` runs immediately and every 12 hours (`collection_worker.go:29-53`).
2. It creates collection tables at runtime (`:56-114`) in addition to migrations.
3. It seeds initial stats/categories/auctions with constants (`:174-242`).
4. It scrapes GetGems aggregate stats and Fragment pages using HTML/regex (`:280-440`).
5. Failed stats/listing fetches preserve/copy previous values or use defaults (`:443-669`).
6. `CollectionRepo` reads latest daily snapshot and child rows (`collection_repo.go:47-150`).
7. Repository computes F&G deterministically from date (`:77-83`) rather than reading a market source.
8. Frontend adds static Hall of Fame and synthetic history chart (`CollectionInfoPage.tsx:52-143`; `UsernameCollectionChart.tsx:27-89`).

# Final assessment

The architecture is feature-rich and has useful safeguards—canonical username validation, Fragment parser fixtures, circuit breaker behavior, singleflight, advisory locks, cache TTLs, and AVM reasoning/audit structures. However, the current product presentation outruns the data contract: synthetic/fallback/static values can look live, verified, or on-chain; monetary access paths are not fully atomic/owner-scoped; and the API/documentation surface has drifted.

**Release recommendation:** do not treat the collection page as a market-data product, and do not treat the certificate or payment/report flows as production-safe, until all P0 findings and the relevant P1 provenance/contract findings are resolved and covered by integration tests.
